# Diagnóstico de NexaTech

Auditoría del 20 de noviembre de 2026. NexaTech tiene una interfaz de tienda compilable y un sitio alojado en Firebase. La persistencia comercial está pendiente. Cloud SQL tiene una instancia activa y SQL Connect tiene un esquema remoto efímero sin conexión a ella.

## Repositorio y ejecución

| Evidencia | Resultado |
| --- | --- |
| Git al iniciar | `main` alineada con su referencia local `origin/main`, último commit `87f79da`, sin cambios preparados. `firebase.json` tenía cambios propios del usuario. `.firebase/.graphqlrc` y los archivos de `dataconnect/` estaban sin seguimiento. `.firebaserc` está versionado y selecciona `nexatech-58ce3`. Git se ejecutó con el binario incluido en GitHub Desktop. |
| Entorno auditado | Node 26.13.1, npm 11.20.0, Firebase CLI 15.36.0 y binario local del emulador SQL Connect 3.4.28. El entorno LTS de la implementación se fijará y comprobará en la fase local. |
| Versiones resueltas | React y React DOM 19.2.8, React Router DOM 7.18.3, Lucide React 1.35.0, Vite 8.2.2, plugin React de Vite 6.1.1 y ESLint 10.9.1. El manifiesto y el lockfile carecen del SDK web de Firebase y del SDK generado. |

App contiene el router, las vistas y los datos. `src/pages/` contiene prototipos no importados, incluido `orderconfirmation.jsx`. Contextos, layout, hook de almacenamiento y archivo separado de productos tienen cero bytes. |

## Firebase y PostgreSQL

| Componente | Configuración local | Evidencia remota |
| --- | --- | --- |
| Hosting | `firebase.json` sirve `dist` y reescribe rutas de cliente a `index.html`. | Respuestas HTTP y recurso JavaScript confirmados. |
| Authentication | Formularios en React. La aplicación no tiene inicialización, proveedores ni observador de sesión de Firebase. | La consulta administrativa de configuración devolvió HTTP 404 `CONFIGURATION_NOT_FOUND`. El proveedor correo/contraseña queda pendiente de configurar y verificar primero en el emulador. |
| SQL Connect | `dataconnect.yaml` declara `nexatech-store`, `us-south1`, `nexatech-postgres` y `fdcdb`. El emulador apunta a `dataconnect/.dataconnect/pgliteData`. `schema.gql` tiene 0 bytes. `connectorDirs` apunta a `example`, cuyo YAML solicita generar el SDK React pero carece de archivos de operaciones `.gql`. | `firebase dataconnect:services:list --project nexatech-58ce3 --non-interactive --json` devolvió el servicio en `us-south1`, los campos de origen vacíos y cero conectores. El GET de `schemas/main` devolvió `postgresql: { unlinked: true, ephemeral: true }`. Es el estado de metadatos que explica la ausencia de origen Cloud SQL detrás del antecedente `MISSING_DATASOURCE`. |
| Cloud SQL | El nombre de instancia y base del YAML expresa la intención local. | Cloud SQL Admin confirmó `nexatech-postgres` en `us-south1`, `RUNNABLE`, `POSTGRES_18`. El GET de `fdcdb` devolvió 404 y la lista de bases devolvió solo `postgres`. La base de aplicación y su vínculo están pendientes. |

Las verificaciones remotas se limitaron a metadatos y respuestas del sitio público. El plan Spark procede de la descripción del titular y la fecha de expiración de esta instancia queda por confirmar. Firebase documenta que la prueba Spark dura 90 días antes del archivado. Para una eventual vinculación, el destino propuesto es la instancia existente y la base `fdcdb`, cuya creación requeriría autorización si sigue ausente. [Administración de bases en SQL Connect](https://firebase.google.com/docs/sql-connect/manage-services-and-databases) · [Cloud SQL Admin API](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1beta4/databases/get) · [Condiciones de Spark](https://firebase.google.com/docs/sql-connect/pricing)

El preludio local ya enumera `Int64`, `@table`, `@ref`, `@unique`, `@index`, `@default`, `@auth`, `@check`, `@redact` y `@transaction`. El SDK anterior falló durante la inicialización según el relato del usuario. La falta de operaciones locales se comprobó al inspeccionar el conector. La compilación del esquema y la generación del SDK pertenecen a la fase de implementación local. [Referencia de directivas](https://firebase.google.com/docs/reference/sql-connect/gql/directive)

## Módulos y brechas académicas

El PDF *Diseño y desarrollo de una tienda virtual*, de la materia Temas Selectos de Tecnología de la Información, se consultó como referencia académica de 15 páginas. Las páginas indicadas pueden usarse para enlazar requisitos con sus futuras pruebas.

| Módulo | Estado | Evidencia y criterio de cierre |
| --- | --- | --- |
| Hosting y compilación | Funcional y comprobado | Compilación exitosa y respuestas de Hosting para tres rutas con reescritura SPA. El 200 de una ruta acredita la entrega de la aplicación, no la ejecución de acciones comerciales. |
| Interacciones de navegación y carrito local | Funcional y comprobado | En Chrome local se probaron búsqueda, categoría, ficha, favoritos y edición del carrito con el catálogo estático. |
| Inicio, catálogo, búsqueda y ficha | Implementado parcialmente | App tiene seis productos estáticos en seis categorías, búsqueda por nombre, filtro de categoría, orden por precio o calificación y ficha con una imagen, acabado fijo y existencias fijas. Las reseñas y cifras son datos de muestra. Un ID desconocido elige el primer producto. Faltan 15 productos semilla distribuidos en tres categorías para la evidencia académica, SKU, peso y dimensiones cuando apliquen, galería, selección de variante, paginación y filtros por precio y disponibilidad. PDF pp. 3–5, 11. |
| Carrito y favoritos | Implementado parcialmente | `nexa-cart` guarda objetos de producto y cantidades. `nexa-favs` guarda IDs. Ambos están en `localStorage` del navegador y se comparten entre quienes usen ese perfil de navegador. Los importes y el límite usan los datos copiados. Falta persistencia por cuenta, gestión del carrito activo y revalidación de cantidades. PDF pp. 2, 4–5, 7. |
| Checkout y cuenta | Implementado parcialmente | `Checkout` y `Auth` contienen formularios sin controlador de envío, autenticación ni lógica de negocio. El carrito muestra envío gratis de forma fija. Checkout muestra la suma del cliente, sin cotizar envío, impuestos, cupones ni total definitivo y sin registrar términos. Faltan registro, inicio y cierre de sesión, recuperación de prueba, perfil y direcciones. PDF pp. 2, 4–5, 7. |
| Pagos, pedidos y comprobante | Pendiente de implementar | Falta el recorrido de pago simulado con folio, pedido persistente, historial, detalle y notificación. El archivo de confirmación es un encabezado fuera del router. PDF pp. 2, 5, 7, 11, 14. |
| Inventario y panel administrativo | Pendiente de implementar | Las seis cifras de stock son constantes del catálogo. Faltan ajustes, alertas, movimientos y protección concurrente, además de administración de catálogo, clientes, pedidos, promociones, inventario y reportes. PDF pp. 4–6, 11. |
| Promociones y reseñas | Implementado parcialmente | Precios anteriores, etiquetas y conteos son datos estáticos. Faltan reglas de vigencia y límites de cupones, moderación, historial de canjes y cálculo autorizado de descuentos. PDF pp. 2, 4–5. |
| Logística, seguimiento y soporte | Implementado parcialmente | Hay textos sobre beneficios y un enlace a una sección de inicio. Los enlaces de ayuda del pie son elementos sin destino. Faltan cobertura, costos y plazos, guía, eventos de envío, canal público y tickets con folio, mensajes y respuestas. PDF pp. 4, 7. |
| Cancelaciones, devoluciones y garantías | Pendiente de implementar | El sitio publica una mención comercial de devolución. Faltan política versionada, solicitud, evidencia, inspección, resolución, reembolso o reposición y al menos tres pruebas de escenarios. PDF pp. 7–8, 11, 14. |

| Documentos, privacidad y políticas | Pendiente de implementar | El pie identifica el sitio como académico. Faltan términos, aviso de privacidad, matriz legal, contacto, FAQ y textos coherentes sobre pago, envíos, cancelaciones, devoluciones y garantías. El tratamiento fiscal y las promesas comerciales requieren revisión antes de publicarse. PDF pp. 4, 8–10, 15. |
| Reportes, respaldo y manuales | Pendiente de implementar | El README describe la plantilla de Vite. Faltan reportes con base real, restauración demostrada, API documentada, manuales, ficha técnica y evidencias de aceptación. PDF pp. 5–7, 11–15. |
| Usabilidad y accesibilidad | Implementado parcialmente | CSS incluye una media query a 800 px. Se observan imágenes sin texto alternativo y controles icónicos sin nombre accesible. Falta comprobar navegación por teclado, etiquetas, contraste, foco, estados de carga/error y anchos desde 360 px en dos navegadores. PDF pp. 3–4, 11. |

El criterio de aceptación del PDF es una compra desde el catálogo hasta su consulta administrativa, pasando por carrito, dirección, entrega, pago de prueba y descuento de inventario, sin intervención directa en la base. La presentación también exige demostrar falta de inventario y un caso de devolución o garantía. Los entregables de análisis de mercado, competidores, requisitos, backlog, identidad, wireframes, cronograma y RACI son trabajo académico adicional a la integración técnica. El PDF admite GraphQL justificado y un pago simulado o sandbox. NexaTech usará un simulador en la primera entrega operativa.

El [modelo relacional](modelo-relacional.md) define la persistencia y la [arquitectura y validación](arquitectura-y-validacion.md) desarrolla las operaciones, las pruebas y la secuencia de implementación.
