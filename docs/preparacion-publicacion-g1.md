## Verificación de PostgreSQL antes de habilitar escrituras

El catálogo [schema-audit.sql](../scripts/schema-audit.sql) captura en una transacción de solo lectura tablas, columnas, constraints, definiciones y validez de índices, disparadores y su habilitación, rutinas, vistas y políticas. Cada línea es un objeto. El ensayo D difirió el esquema mediante el emulador, detectó **32 `CHECK`, 72 FK y 7 índices parciales** cambiados o retirados y comprobó también que el inventario detecta un disparador deshabilitado. Se restauraron las 111 definiciones en una transacción. La detección en `commerce_schema_ready()` rechazó los comandos con `SCHEMA_INCOMPLETE` cuando faltaban protecciones críticas. Esa función comprueba un subconjunto durante la ejecución. La comparación de catálogo, permisos y pruebas funcionales es el control de publicación.

1. Generar una referencia nueva desde la misma revisión de Git que se publicará. Establecer las variables de PostgreSQL 18 de la [guía local](implementacion-local.md) y apuntar `NEXATECH_G1_SCHEMA_REFERENCE` a un archivo inexistente. Ejecutar `npm.cmd run test:postgres18`. La referencia contiene DDL y se genera antes de provocar deriva. Guardar su SHA-256 junto con la revisión, las versiones de las herramientas y las sumas de las migraciones.
2. Desde una conexión autorizada a `fdcdb` mediante Cloud SQL Auth Proxy sobre loopback, confirmar destino, `current_database()`, `server_version_num`, usuario y esquema. Usar credenciales IAM u otro acceso aprobado fuera del navegador. Ejecutar las comprobaciones con un auditor PostgreSQL y un rol separado para migraciones. Los documentos o logs de ejecución deben omitir DSN con contraseña, tokens y datos de compradores. [Cloud SQL Auth Proxy](https://cloud.google.com/sql/docs/postgres/sql-proxy) · [Ingreso con IAM](https://cloud.google.com/sql/docs/postgres/iam-logins)
3. Tomar una instantánea antes y después de cada paso que aplique DDL, cambie privilegios o publique el esquema. Usar UTF-8 y conservar cada archivo fuera de Git. El ejemplo supone que la sesión administrativa ya configuró `PGHOST`, `PGPORT`, `PGUSER` y credenciales seguras para el proxy. La comparación debe terminar con salida cero. Toda diferencia se revisa antes de abrir operaciones, incluidas diferencias de representación entre 18.7 local y 18.6 administrado. Una equivalencia de representación se demuestra en PostgreSQL y se registra por objeto.

   ```powershell
   $env:PGCLIENTENCODING = 'UTF8'
   psql -XAtq -v ON_ERROR_STOP=1 -d fdcdb -f scripts/schema-audit.sql -o candidato.jsonl
   if ($LASTEXITCODE -ne 0) { throw 'No se pudo leer el catálogo' }
   git diff --no-index --ignore-cr-at-eol referencia.jsonl candidato.jsonl
   if ($LASTEXITCODE -ne 0) { throw 'Publicación detenida por diferencia de esquema' }
   ```

4. Confirmar las 40 tablas `public`, el registro `nexa_migrations.applied`, el propietario de los objetos y la versión/hash de cada migración. `pg_catalog` y los nombres calificados deben resolver las rutinas y tablas esperadas. Verificar las funciones `SECURITY DEFINER`, sus propietarios, `search_path` y que `PUBLIC` carezca de acceso a `nexa_internal`. Probar `SELECT nexa_internal.commerce_schema_ready()` como propietario antes de habilitar los conectores. Aplicar [runtime-audit.sql](../scripts/runtime-audit.sql) al **login efectivo del servicio** y comprobar que devuelve cero filas. El script detecta permisos de propiedad, DDL, DML directo, `INSERT` adicionales y acceso a rutinas internas. Validar también quién puede asumir el login o los roles de grupo desde IAM/PostgreSQL.

   ```powershell
   $fallas = psql -XAtq -v ON_ERROR_STOP=1 -v "nexa_runtime=$loginServicio" -d fdcdb -f scripts/runtime-audit.sql
   if ($LASTEXITCODE -ne 0 -or $fallas) { throw "Publicación detenida. $fallas" }
   ```

5. El CLI 15.36.0 concede `SELECT, INSERT, UPDATE, DELETE` amplios al rol PostgreSQL de escritura en su configuración estándar, incluso mediante privilegios predeterminados. En el flujo con DDL propio, declinar administración automática del esquema, mantener propietario separado y limitar el rol de ejecución a las lecturas requeridas y los `INSERT` por columna de `app_user` y `commerce_command`. Tratar el servicio administrado como la frontera que impone UID y roles GraphQL. Verificar en el destino si admite este recorte y si lo conserva al desplegar o reenlazar. Si restablece DML amplio o falla con privilegios mínimos, bloquear publicación hasta resolverlo. Probar bajo la identidad efectiva, mediante el SDK, `EnsureProfile`, `GetMyProfile` y una compra, además de permisos negativos y acceso a vistas. [Integración con DDL propio y roles de SQL Connect](https://firebase.google.com/docs/sql-connect/manage-services-and-databases#integrate_existing_cloud_sql_for_postgresql_databases)

## Secuencia de ejecución futura

Registro del escenario Cloud SQL de G1. Esta secuencia queda suspendida mientras Firebase no confirme una vía oficial para terminar la prueba existente dentro de Spark. Para un backend alternativo se aplican los controles de PostgreSQL, Authentication y Hosting con la API elegida.

1. **Configurar la base.** Confirmar la revisión de Git y preparar la lista de archivos de cambios existentes, incluidos los que todavía carecen de seguimiento. Revalidar instancia, vencimiento, facturación, permisos y destino. Tras autorización, crear únicamente `fdcdb` en `nexatech-postgres` si sigue ausente. Configurar el acceso del propietario de migraciones y del servicio. Conservar evidencia de que el destino está vacío o sacar un respaldo antes de tocarlo.
2. **Vincular.** Desde el asistente oficial, seleccionar la instancia y la base aprobadas en `us-south1`. Usar el flujo de base existente. Si se utiliza `dataconnect:sql:setup` del CLI 15.36.0, autorizarlo explícitamente porque puede vincular el esquema y configurar identidades/grants. Elegir DDL administrado por el proyecto y separar permisos. Verificar por GET que ya aparecen la instancia y `fdcdb` y que el origen dejó de ser efímero. [Gestión de SQL Connect y Cloud SQL](https://firebase.google.com/docs/sql-connect/manage-services-and-databases)
3. **Validar y transferir DDL.** Una vez confirmado el vínculo y APIs habilitadas, inspeccionar `firebase.cmd dataconnect:sql:diff --project nexatech-58ce3 --service nexatech-store --location us-south1`. El CLI revisado puede llamar a habilitación de APIs y usa la actualización de esquema con validación, por lo que queda para la etapa autorizada. Guardar y ensayar el DDL en PostgreSQL desechable antes de aplicar el baseline. Mantener `schemaValidation: COMPATIBLE` explícito. Ese modo protege objetos ajenos en ciertos casos y admite cambios requeridos de nulabilidad u otros ajustes. `STRICT` exige coincidencia exacta y puede eliminar objetos o columnas adicionales. El modo implícito del CLI puede ofrecer cambios estrictos tras los compatibles. Parar ante `DROP`, `CASCADE`, pérdida de `NOT NULL`, cambio de FK/índice/disparador o cualquier diferencia sin revisar. Evitar `--force`, `dataconnect:sql:migrate` automático y opciones sin validación. [Modos de validación](https://firebase.google.com/docs/sql-connect/manage-schemas-and-connectors) · [CLI](https://firebase.google.com/docs/sql-connect/cli-reference)
4. **Aplicar las cinco migraciones complementarias.** Con PostgreSQL en mantenimiento, cargar el baseline revisado, después `001_constraints.sql` a `005_dispatch.sql` en orden. Reproducir el mecanismo local de [local-dataconnect.mjs](../scripts/local-dataconnect.mjs). Crear el registro privado de migraciones, serializar los cambios y aplicar cada SQL y su registro en la misma transacción. El hash normaliza los saltos `CRLF` a `LF`. Ante un checksum distinto o deriva, detener y restaurar a partir del catálogo/respaldo. Conservar el registro y el DDL aplicado. Comparar catálogo y permisos con los controles anteriores. [Modelo relacional](modelo-relacional.md)
5. **Publicar los contratos.** Aprobar por separado `firebase.cmd deploy --only dataconnect:nexatech-store:schema --project nexatech-58ce3` una vez que el diff compatible sea inocuo. El CLI aún tiene rutas de migración y aprovisionamiento. Abortar ante propuestas de cambios no aprobados y revalidar las protecciones inmediatamente después. Desplegar `dataconnect:nexatech-store:storefront`, `dataconnect:nexatech-store:account` y `dataconnect:nexatech-store:staff` con `firebase.cmd deploy --only <selector> --project nexatech-58ce3`. Verificar cada lista de operaciones y revalidar los grants después. Las vistas `@view` se definen en GraphQL. En el emulador las consultas funcionan sin crear vistas físicas, por lo que el inventario SQL se complementa con la revisión de `staff.gql` y pruebas de acceso. Mantener el frontend candidato fuera de `live` hasta pasar las pruebas. [Publicación de esquemas y conectores](https://firebase.google.com/docs/sql-connect/manage-schemas-and-connectors)
6. **Habilitar Authentication y aplicación web.** Seguir el procedimiento de la sección siguiente. Aprovisionar solo las cuentas de prueba aprobadas. Confirmar que `CUSTOMER`, `ADMIN` y `SUPPORT` siguen dependiendo de PostgreSQL y que los conectores de personal requieren correo verificado.
7. **Cargar y conciliar datos.** En la base de destino comprobada, aplicar `demo.sql` y `catalog-e1.sql` juntos en una transacción con `ON_ERROR_STOP`. Construir solo desde estas semillas y conservar las claves por `slug`, SKU y las imágenes identificadas. Ejecutar dos veces en el ensayo, comprobar 153 fichas, seis categorías, 50 en cada categoría principal, cero SKU duplicados, ninguna salida/movimiento nuevo por reintento y conciliación `stock_on_hand = sum(delta)` por variante, incluidas las agotadas. Las semillas no crean cuentas de Auth ni copian pedidos del emulador. Mantener evidencia de la etiqueta académica, de las seis políticas de demostración y del proveedor `SIMULATED`. [Catálogo y atribución](catalogo-e1.md)
8. **Pruebas de backend.** Con los conectores e identidades autorizadas, verificar catálogo, perfiles, carrito entre sesiones, cotización, compra aprobada y rechazo por inventario con cuentas académicas. Cotejar folio, partidas, aceptación, pago, movimientos y auditoría con PostgreSQL. Comprobar permisos con cuentas ajenas y `SUPPORT` y probar cancelación y devolución o garantía. Usar la base autorizada y registrar los efectos de los datos de demostración.
9. **Vista previa y E2E.** Publicar al canal temporal del sitio existente tras autorización. Abrir rutas directas y recargar, probar registro, acceso, recuperación, permisos, checkout, PDF, seguimiento y soporte con Chrome y Edge, y comprobar que el navegador solo usa HTTPS para Auth y SQL Connect. La vista previa usa el backend de ese proyecto. Identificar las escrituras de prueba y evitar datos personales de terceros. Registrar versión y resultado. [Vista previa de Hosting](https://firebase.google.com/docs/hosting/test-preview-deploy)
10. **Publicación principal.** Esperar la aprobación explícita luego del E2E. Promover exactamente la versión de Hosting validada. Verificar la URL pública y los recorridos aprobados después de la promoción. La documentación institucional definitiva y la matriz F se completan tras comprobar la URL pública.

## Publicación y reversión

Compilar primero con `npm.cmd run build` y verificar `dist`. La configuración de Hosting sirve ese directorio, reescribe `**` a `/index.html` para React y vuelve a compilar en `predeploy`. Aprobado el canal temporal, usar `firebase.cmd hosting:channel:deploy g1-validacion --expires 7d --no-authorized-domains --project nexatech-58ce3`. La opción evita que el CLI cambie dominios de Auth como efecto del despliegue. Autorizar el dominio del canal separadamente si las pruebas lo requieren. Al aprobar la publicación principal, usar `firebase.cmd hosting:clone nexatech-58ce3:g1-validacion nexatech-58ce3:live --project nexatech-58ce3`. Registrar el ID de la versión anterior y de la promovida. Para revertir Hosting, seleccionar la versión anterior en el historial de releases. [Canales, clonación y reversión](https://firebase.google.com/docs/hosting/manage-hosting-resources)

Antes de habilitar escrituras, y antes de cada migración futura, guardar `pg_dump --format=custom` de `fdcdb` por una conexión autorizada, junto con SHA-256, instantánea del catálogo, sumas del registro, manifiesto de propietarios/grants y referencia de versiones de GraphQL y Hosting. Guardar el respaldo cifrado y con acceso restringido. Restaurar con `pg_restore --exit-on-error --single-transaction` sobre una base desechable vacía, ajustando propietarios y ACL del destino con el manifiesto aprobado si se usó `--no-owner --no-privileges`. Comparar DDL y datos, verificar referencias y ejecutar una compra en la copia. Usar respaldos administrados y PITR solo cuando estén habilitados y autorizados. [Respaldos Cloud SQL](https://cloud.google.com/sql/docs/postgres/backup-recovery/backups) · [pg_dump PostgreSQL 18](https://www.postgresql.org/docs/18/app-pgdump.html) · [pg_restore PostgreSQL 18](https://www.postgresql.org/docs/18/app-pgrestore.html)

Si una verificación falla, detener escrituras en el conector o en PostgreSQL mediante el cambio aprobado, guardar evidencia y respaldo del estado fallido y evaluar el volumen de cambios desde el último respaldo. Revertir primero la capa incompatible mediante la versión de Hosting o los contratos anteriores. Restaurar o corregir el esquema en una copia, reconciliar pedidos y UID posteriores al respaldo antes de un cambio de destino, y volver a ejecutar catálogo, permisos y E2E. La reversión de Hosting no modifica PostgreSQL ni Authentication. Los respaldos de `fdcdb` conservan los UID, y las identidades de Firebase Auth se administran por separado. Una restauración sobre una base existente, la recreación de conectores y una nueva instancia requieren aprobación específica.

## Acciones remotas que requieren autorización

| Autorización | Cambios incluidos |
| --- | --- |
| Facturación | Fuera del alcance por restricción definitiva. Firebase permanece en Spark y los demás servicios deben usar planes Free. |
| Backend alternativo | Crear el proyecto gratuito elegido, su base, identidad de ejecución, migraciones, semilla, respaldo y servicio API. |
| Cloud SQL | Secuencia suspendida. Si Firebase confirma una vía en Spark para la prueba existente, cualquier creación de `fdcdb` o cambio de acceso, esquema o vínculo requiere autorización específica. |
| SQL Connect y PostgreSQL en Cloud SQL | Secuencia suspendida. Cualquier `sql:setup`, migración, cambio de grants o despliegue de conectores requeriría que Firebase confirme primero un flujo oficial para la prueba en Spark. |
| Authentication | Registrar la app web, inicializar Authentication, habilitar proveedor, editar dominios, plantillas o política, crear o quitar identidades de prueba y aprovisionar `ADMIN`/`SUPPORT`. |
| Datos y pruebas | Cargar la semilla académica en `fdcdb`, ejecutar los E2E que escriben pedidos, stock, cupones, expedientes o mensajes y depurar esos datos según el procedimiento aceptado. |
| Hosting | Crear y desplegar `g1-validacion` en el sitio existente. Publicar en `live` mediante una aprobación posterior distinta. Cualquier reversión, cierre del canal o cambio de dominios requiere autorización. |
